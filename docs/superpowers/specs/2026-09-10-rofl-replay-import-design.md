# .rofl 리플레이 임포트 설계

**날짜:** 2026-09-10
**상태:** 설계 승인 대기

## 배경 및 목적

내전 결과는 지금 관리자가 `/matches`의 `MatchBuilder`에서 손으로 넣는다. 10명을 두 팀에
앉히고 승리 팀을 고르는 작업이다. 그런데 LoL 클라이언트가 저장하는 리플레이 파일
(`.rofl`)에는 그 입력에 필요한 값이 전부 들어 있다 — 참가자의 Riot ID, 팀, 승패, 경기
길이. 파일을 올리면 매칭해서 채워주는 것이 이 기능의 목적이다.

부수적으로 두 가지를 더 얻는다. 첫째, 리플레이는 **그 사람이 그 경기를 뛰었다는 1차
증거**라서 회원의 라이엇 신원을 확정하는 가장 정확한 출처다. 둘째, AFK·탈주·항복 여부가
파일에 있어 MMR 반영 전에 기계적으로 검증할 수 있다.

## 범위 밖

- **좌표·와드·킬 로그.** 리플레이 앞쪽 청크(zstd)를 풀어 그 안의 패킷을 해석해야
  얻어지고, 패킷 구조는 패치마다 바뀐다. 참고한
  [Mowokuma/ROFL](https://github.com/Mowokuma/ROFL)은 2025-03 기준이고 2025-11에
  아카이브됐다. 실질적으로 별개 프로젝트이므로 하지 않는다.
- **개인 스탯 저장.** 메타데이터에 참가자당 371개 키가 있지만(KDA, 딜량, 시야점수, 핑
  횟수 등), 이번 목적은 결과 입력 자동화다. 스탯 테이블과 전적 상세 화면은 후속으로
  둔다. 다만 매칭 화면에는 사람이 누구인지 알아보는 단서로 챔피언·포지션·KDA를 띄운다.
- **Riot API 연동.** 계정 조회도 경기 조회도 하지 않는다. 파일만 읽는다.
- **회원 즉석 생성.** 리플레이에 나왔지만 회원 목록에 없는 사람은 "회원 아님"으로
  처리한다. 아래 "검토한 대안" 참고.

## .rofl 파일 포맷 (실측)

`data/KR-8374660628.rofl`(13.8MB, 패치 16.17.810.4348)을 직접 뜯어 확인한 레이아웃이다.
매직이 `RIOT` 뒤 `02 00`인 이른바 ROFL2 형식이다.

| 오프셋 | 내용 |
|---|---|
| `0x00` | `RIOT` + `02 00` |
| `0x06` | 용도 미확인 8바이트 |
| `0x0E` | 버전 문자열 길이 (u8, 실측 14) |
| `0x0F` | 버전 문자열 (`16.17.810.4348`) |
| `0x1D` | 첫 청크 헤더 17바이트 — id(u32) / type(u8) / id2(u32) / 원본길이(u32) / 압축길이(u32) |
| `0x2E` | zstd 프레임 매직 `28 B5 2F FD` — 페이로드 시작 |
| 끝 − 4 | 메타데이터 JSON 길이 (u32 LE, 실측 122,835) |
| 끝 − 4 − N | **평문 JSON** (압축도 암호화도 없음) |

핵심은 **필요한 것이 전부 파일 맨 뒤 평문 JSON에 있다**는 점이다. 파서는 마지막 4바이트를
읽어 길이를 얻고 그만큼 앞에서 잘라 `JSON.parse`한다. 앞쪽 청크는 열지 않으므로 zstd
의존성도, 패치 종속성도 생기지 않는다.

JSON의 모양:

```
{ gameLength: 1584502, lastGameChunkId, lastKeyFrameId, statsJson: "<참가자 10명 배열의 JSON 문자열>" }
```

`statsJson`은 한 번 더 문자열로 감싸여 있어 두 번 파싱해야 한다. 참가자에서 쓰는 키:

| 키 | 쓰임 |
|---|---|
| `PUUID` | 계정 정체성. 인게임 닉을 바꿔도 불변 |
| `RIOT_ID_GAME_NAME`, `RIOT_ID_TAG_LINE` | 표시용 표기, 매칭 대상 문자열 |
| `TEAM` (`100`/`200`) | BLUE / RED |
| `WIN` (`Win`/`Fail`) | 승리 팀 판정 |
| `TEAM_POSITION` | TOP / JUNGLE / MIDDLE / BOTTOM / UTILITY |
| `SKIN` | 챔피언 |
| `CHAMPIONS_KILLED`, `NUM_DEATHS`, `ASSISTS`, `LEVEL`, `MINIONS_KILLED`, `NEUTRAL_MINIONS_KILLED` | 화면에 띄우는 식별 단서 |
| `WAS_AFK`, `WAS_LEAVER`, `TIME_SPENT_DISCONNECTED`, `GAME_ENDED_IN_SURRENDER` | 경기 검증 |

`NAME`은 빈 문자열이다. 참고 저장소가 참가자 순서를 `i % 5`로 추정한 이유가 이것인데,
`RIOT_ID_*`와 `TEAM_POSITION`이 채워져 있으므로 그럴 필요가 없다.

**파일에 없는 것:** 경기 날짜/시각(길이만 있다), 밴 정보, 아이템 구매 타임라인(최종 6칸만),
솔로랭크 티어, 오브젝트 타임라인.

## 데이터 모델

### RiotAccount (신규)

```prisma
model RiotAccount {
  id          String    @id @default(uuid())
  // null이면 "회원 아님"으로 확정한 외부인 계정. 다음 업로드에서 다시 묻지 않으려고 남긴다.
  memberId    String?
  member      Member?   @relation(fields: [memberId], references: [id])
  // 리플레이에서만 얻는다. 인게임 닉을 바꿔도 변하지 않는 유일한 값이라 이 테이블의 정체성이다.
  puuid       String    @unique
  // 마지막으로 관측된 표기. 닉변하면 갱신한다. 화면 표시용이며 매칭의 근거가 아니다.
  gameName    String
  tagLine     String
  firstSeenAt DateTime  @default(now())
  lastSeenAt  DateTime

  @@index([memberId])
}
```

한 회원이 여러 계정을 가질 수 있으므로 `Member` 1 : N `RiotAccount`다. 부계정은 처음 한
번만 물어보면 그 뒤로는 본계·부계 구분 없이 자동으로 붙는다.

**행은 리플레이에서 관측된 계정으로만 만든다.** 카톡·디코 닉네임에 적힌 Riot ID로는 절대
행을 만들지 않는다. 그 값들은 사람이 손으로 적은 것이라 오타·태그 누락·띄어쓰기 차이가
흔하고, 그대로 저장하면 `박병준#0216`(리플레이)과 `박병준#kr1`(카톡 오기)이 별개 계정이
되어 중복이 늘어난다. 그것들은 계정이 아니라 **매칭 힌트**로만 쓴다. `puuid`가 non-null
unique이므로 같은 계정이 두 번 등록될 수 없다.

### Member (변경 없음)

`Member.riotId`는 그대로 둔다. 지금도 관리자가 손으로 적어둔 표기이고 멤버 표와 팀
빌더에 보이고 있다. 역할만 명확히 한다 — **표시 + 매칭 힌트**이며 계정의 출처가 아니다.

`tier`와 `mmr`도 `Member`에 그대로 둔다. 부계정 티어가 본계와 달라도 팀 빌더가 재는 것은
사람의 실력이고, 계정별로 티어를 두면 "오늘 어느 계정으로 들어왔느냐"에 따라 팀 편성이
흔들린다.

### GameResult (컬럼 추가)

```prisma
  // 같은 리플레이의 재업로드를 막는다. 정렬한 PUUID 10개 + gameLength의 SHA-256.
  // 파일명에 의존하지 않으므로 이름을 바꿔 올려도 같은 값이 나온다.
  replayKey String? @unique
```

카톡 임포트는 워터마크로 멱등성을 얻지만(`max(MentionLog.mentionedAt)`), 리플레이는 시간
축이 없으므로 내용 해시로 잡는다. 손으로 입력한 경기는 `null`이다.

## 매칭

### 신뢰 등급

| 출처 | 정확도 | 역할 |
|---|---|---|
| 리플레이 `PUUID` | 확정 | `RiotAccount`의 유일한 출처 |
| 리플레이 `gameName#tagLine` | 정확(닉변 시 변함) | 표시용 스냅샷 |
| 카톡 `이름/나이/RiotID`의 3번째 조각 | 부정확 | 힌트 |
| 디코 `이름/RiotID/가능포지션`의 2번째 조각 | 부정확 | 힌트 |
| `Member.riotId` | 부정확 | 힌트 |

### 새 순수 함수 (`packages/core`)

- **`parseRoflMetadata(bytes: Uint8Array): Replay`** — 꼬리 JSON만 읽는다. 파일 I/O는
  호출자가 하므로 `packages/core`의 "I/O 없음" 규칙을 지킨다.
- **`kakaoRiotHint(nickname)`** — `이름/나이/RiotID`에서 3번째 조각. 나이 자리가 숫자일
  때만 관례로 인정한다. `kakaoMatchKey`가 쓰는 판정과 같다.
- **`discordRiotHint(displayName)`** — `이름/RiotID/가능포지션`에서 2번째 조각과, 3번째
  조각을 리플레이 포지션 표기(`TOP`/`JUNGLE`/…)로 옮긴 배열.
- **`scoreRiotAccountMatch(player, member): { score, reasons }`**

점수:

| 신호 | 점수 | 근거 라벨 |
|---|---|---|
| 힌트가 `gameName#tagLine` 또는 `gameName`과 일치 | 100 | `카톡ID일치` / `디코ID일치` / `등록ID일치` |
| 힌트가 접두·접미 관계 | 60 | `카톡ID유사` / `디코ID유사` / `등록ID유사` |
| 실명(또는 성을 뗀 조각)이 `gameName`에 포함 | 45 | `실명조각` |
| 디코 가능 포지션에 이번 경기 포지션이 있음 | +25 | `포지션일치` |

비교는 전부 기존 `normalizeForMatch`를 거친다 — 대소문자·공백·`#._-`가 접히므로
`Pink Taric Boy#KR2`와 `PinkTaricBoy`가 같은 값이 된다. 힌트 점수는 카톡·디코·`riotId`
중 **최댓값 하나만** 취한다(같은 사실을 세 번 세지 않는다).

**포지션은 가산점 전용이다.** 다른 신호가 0이면 후보로 만들지 않는다. 포지션만으로 후보를
세우면 UTILITY 슬롯 하나에 서폿 회원이 전부 같은 점수로 딸려 나와 목록이 무의미해진다.

자동 배정은 `점수 >= 100 && 1위−2위 >= 40`일 때만 한다(`isAutoAssignable`). 기존
`isSoleCandidate`와 같은 사고방식이지만 임계값이 다르므로 별도 함수로 둔다.

**상호 배타:** 이미 다른 슬롯에 배정된 회원은 남은 슬롯의 후보에서 제외한다. PUUID 확정을
먼저 돌려 배정 집합을 채운 뒤 나머지를 채점한다.

픽션 데이터(카톡 export, 디코 명단, `.rofl`)에 어려운 케이스를 심고 위 함수를 돌린 결과다.
카톡 파싱은 저장소의 `parseKakaoExport`, 디코 연결은 기존 `scoreAccountMatch`를 그대로
썼다.

| 케이스 | 리플레이 표기 | 카톡·디코 표기 | 결과 |

| 정확 일치 | `챌린저가고싶나#JBD` | 동일 | 자동 100 |

| 인게임 닉변 | `우성정글#KR1` | `정글의왕#KR1` | 후보 70 · 손 필요 |

| 외부인 | `모든 것을 잃은 사나이#융탄폭격` | — | 후보 없음 |

10명 중 **PUUID 확정 2 / 자동 5 / 후보 제시 1 / 후보 없음 2**. 부계정과 외부인은 카톡·디코
어디에도 단서가 없으니 점수 0이 맞고, 한 번 손으로 고르면 PUUID가 저장돼 다음 업로드부터
확정으로 넘어간다.

## 반쪽 회원 규칙

`saveGameResult`는 참가자 전원이 디코와 카톡 양쪽 다 붙어 있을 것을 요구한다. 리플레이에
반쪽 회원이 한 명만 끼어도 저장이 통째로 거부되므로, 자동화의 의미가 사라진다.

**조건을 넓히되 좁게 넓힌다.** "디코 AND 카톡"에 "**PUUID가 있는 `RiotAccount`가 붙어
있으면 갈음**"을 더한다. 리플레이는 그 사람이 그 경기를 뛰었다는 1차 증거이고, 원래 규칙의
목적이 "이 행이 확실히 정착된 한 사람인가"라면 PUUID로 확정된 계정이 붙은 행은 그 목적을
이미 충족한다. `RiotAccount`는 손으로 만들 수 없으므로 이 완화는 리플레이로 확인된
사람에게만 자연히 적용된다.

`getLinkedMembers`(수동 입력 풀)도 같은 조건으로 넓힌다. 리플레이로 확인된 사람이 수동
입력에서는 못 뜨는 것이 더 놀랍다.

**짝으로 반드시 필요한 것:** 원래 규칙이 막던 것은 "반쪽 행에 쌓인 기록이 병합 때 붕
뜨는" 상황이다. 따라서 `absorbMember`가 흡수 대상의 `GameParticipant`와 `RiotAccount`를
생존자로 옮기고 `releaseMember`가 정확히 되돌려야 한다. 생존자와 흡수 대상이 같은 경기에
둘 다 들어 있으면 `@@unique([gameResultId, memberId])`가 충돌하므로, 그때는 병합을
거부한다 — `normalizeKakaoNicknames`가 한 그룹에 두 `discordUserId`가 있을 때 배치를
중단하는 것과 같은 방어다.

## 화면

`/replay-import` 새 페이지를 만든다. `/kakao-import`의 형제이고, `AppShell`을 쓰므로
`export const dynamic = "force-dynamic"`이 필요하다. 목업:
https://claude.ai/code/artifact/1639958b-22b8-402f-98fc-ab29d4201484

**파일 헤더** — 파일명, 패치, 경기 길이, 승리 팀. 옆에 검증 칩(AFK 없음 / 탈주 없음 /
항복 아님)과 **미해결 카운터**.

**팀 두 칸, 슬롯 10개.** 슬롯 왼쪽에 상태를 색으로 인코딩한 3px 스트라이프를 둔다 —
녹색(PUUID 확정 · 직접 선택), 파랑(자동), 회색(회원 아님), 호박(미해결). 숫자를 읽지
않아도 무엇이 남았는지 보인다.

**확정된 슬롯은 한 줄로 조용히**, 미해결 슬롯만 펼친다. 10명 중 8명이 자동인데 모달을
10번 띄울 이유가 없다.

**후보는 드롭다운에 숨기지 않고 칩으로 노출한다.** 클릭 한 번에 끝나고, 근거 라벨
(`실명조각 · 포지션일치`)과 점수가 칩 위에 보인다. 자동 확정 문턱 아래인 후보가 왜
1순위인지 관리자가 판단할 수 있어야 잘못된 매칭을 잡아낸다. 그 아래에 전체 회원 검색과
**"회원 아님"** 버튼을 둔다.

**챔피언·포지션·KDA를 크게 띄운다.** 이름 매칭이 실패해도 "와윅 15/2/4 탑"을 보면 사람은
누구인지 안다.

**회원 라벨에 출생연도를 붙인다** (`김민준 / 95`, `김민준 / 01`). 동명이인이 목록에서
구분되지 않는다. 카톡 match key가 이미 `실명/출생연도`이므로 일관된다.

**저장 게이트** — 10명이 모두 해결되기 전에는 저장 버튼이 잠긴다. 절반만 반영된 경기가
MMR을 오염시키는 것을 막는다.

## 저장 흐름

1. 파일 업로드(드래그앤드롭). `KakaoImportForm`의 패턴을 따른다.
2. 서버에서 `parseRoflMetadata`. `RIOT` 매직이 아니거나 JSON이 깨지면 거부한다.
3. `replayKey`를 계산해 이미 저장된 경기면 거부한다("이미 등록된 경기입니다").
4. PUUID로 `RiotAccount`를 조회해 아는 계정을 배정하고, 나머지를 채점해 자동 배정 또는
   후보 제시.
5. 관리자가 미해결을 해결한다. 경기 날짜는 브라우저의 `File.lastModified`를 기본값으로
   채우고 수정 가능하게 둔다 — **파일에 벽시계 시각이 없다.**
6. 저장(`prisma.$transaction`):
   - 새로 확정된 계정을 `RiotAccount`에 만들고, 이미 있는 계정은 `gameName`/`tagLine`/
     `lastSeenAt`을 갱신한다(닉변 반영).
   - "회원 아님"으로 고른 계정은 `memberId: null`로 남긴다 — 다음 업로드에서 다시 묻지
     않는다.
   - 기존 `saveGameResult`를 그대로 호출한다. MMR 계산 경로는 손대지 않는다.
   - 참가한 회원의 `lastActiveAt`을 경기 날짜로 갱신한다. 같이 게임을 했는데 카톡에 글을
     안 썼다고 비활동으로 잡히는 지금의 구멍을 메운다.
7. AFK·탈주가 있으면 저장 전에 경고를 띄우되 막지는 않는다. 판단은 관리자 몫이다.

## 테스트

- `packages/core` — 순수 단위 테스트. `parseRoflMetadata`는 **실제
  `data/KR-8374660628.rofl`과 합성 픽스처 양쪽**에 돌린다(`data/`는 gitignore이므로
  실파일 테스트는 파일이 있을 때만 도는 조건부로 둔다). `scoreRiotAccountMatch`는 위
  실측 표의 7개 케이스를 그대로 테스트로 옮긴다.
- `apps/dashboard` — 실 Postgres 통합 테스트. `DATABASE_URL_TEST` 가드를 넣는다.
  `absorbMember`/`releaseMember`의 `GameParticipant`·`RiotAccount` 이관과 충돌 시 거부를
  두껍게 덮는다. 여기가 이 설계에서 가장 깨지기 쉬운 곳이다.
- `replayKey` 중복 거부, 반쪽 회원 저장 허용/거부 경계도 통합 테스트로 덮는다.

## 검토한 대안

**반쪽 회원 처리 (a) 저장을 막고 링크 화면으로 보낸다** — 기존 규칙을 전혀 건드리지 않아
가장 안전하다. 그러나 10명 중 1명만 반쪽이어도 자동화가 멈추고, 관리자가 화면을 왕복하는
사이 매칭 작업이 날아간다. 기각.

**반쪽 회원 처리 (c) 리플레이 참가자를 즉석에서 회원으로 만든다** — 중복 회원을 양산할
위험이 가장 크다. 카톡에 이미 있는 사람인데 관리자가 못 찾고 새로 만들면 한 사람이 두
행이 된다. 게다가 (b) 없이는 만들어도 경기에 넣을 수 없어 (b)를 전제한다. 카톡·디코 어디에도
없는 사람은 모임 밖 사람일 가능성이 높고 "회원 아님"으로 충분하다. 기각.

**`Member.riotId`를 여러 개 담도록 문자열로 확장(콤마 구분)** — 마이그레이션이 가장 싸지만
PUUID를 담을 자리가 없고 인덱스도 못 건다. 기각.

**카톡·디코에 적힌 Riot ID로도 `RiotAccount` 행을 만든다** — 계정 목록이 빨리 차지만, 그
값들이 부정확해서 같은 사람의 계정이 표기별로 여러 행이 된다. 중복 문제를 푸는 대신 만드는
셈이다. 기각.

**참고 저장소의 Rust 파서를 포팅한다** — 좌표·와드까지 얻으려면 필요하지만 범위 밖이고,
메타데이터만 쓰는 이 설계에는 쓸 것이 없다. 그쪽 메타데이터 파서는 참가자 순서를 `i % 5`로
추정하고 `NAME`이 빈 문자열이라 신원을 포기했는데, 우리는 `RIOT_ID_*`와 `TEAM_POSITION`을
직접 읽으므로 오히려 더 정확하다. 기각.
