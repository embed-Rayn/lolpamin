# Discord ↔ KakaoTalk 통합 설계

**날짜:** 2026-08-23
**상태:** 설계 승인 완료, 구현 계획 작성 대기

## 배경 및 목적

LoL(리그오브레전드) 게임 모임 운영을 위해 두 개의 봇과 하나의 웹 대시보드로 구성된 통합 시스템을 만든다.

- **디스코드 봇**: 관리자가 대시보드에서 입력한 게임 결과를 바탕으로 멤버별 내부 ELO 레이팅을 계산/조회한다.
- **카카오톡 오픈채팅방 봇**: 게임 구인방에서 오가는 `@닉네임` 멘션을 수집해 멤버별 최근 활동 시각을 추적하고, 최근 2주간 활동이 없는 멤버를 관리자가 대시보드에서 확인할 수 있게 한다.
- **통합 문제**: 디스코드와 카카오톡은 동일 인물이라도 닉네임 표기 방식이 다르다 (예: 디스코드 `박병준/늑 구#1003/정글탑`, 카카오톡 `박병준/94/늑 구#0216`). 두 플랫폼의 계정을 "같은 사람"으로 연결해야 ELO와 활동 기록을 하나의 회원 데이터로 관리할 수 있다.

## 범위 밖 (Out of scope)

- 디스코드-카카오톡 간 실시간 메시지 중계(브릿지)는 하지 않는다. 이번 시스템은 신원 통합과 활동/ELO 관리에 집중한다.
- 미활동 경고의 자동 발송(카톡 멘션 발송, 디스코드 DM 발송)은 하지 않는다. 미활동자 목록은 관리자 대시보드에서 확인만 한다.
- 계정 연결(링크)의 자가등록 플로우는 두지 않는다. 관리자가 대시보드에서 수동으로 매핑한다.
- Riot API를 통한 게임 결과 자동 수집은 하지 않는다. 게임 결과는 관리자가 대시보드에 수동 입력한다.

## 아키텍처

모노레포로 구성하고, 하나의 VPS에서 세 개의 독립 프로세스로 배포한다.

```
/apps
  /discord-bot   (discord.js) — ELO 조회 전용
  /kakao-bot     (node-kakao) — 오픈채팅방 메시지 읽기 전용
  /dashboard     (Next.js)    — 회원 매핑, 게임 결과 입력, 미활동자 리포트
/packages
  /db            (Prisma schema + client, 세 앱이 공유)
  /core          (ELO 계산, 미활동 판정 로직 — 순수 함수)
```

세 프로세스는 하나의 Postgres DB를 공유한다. pm2 또는 docker-compose로 각 프로세스를 독립 실행하여, 카카오톡 봇(비공식 프로토콜이라 상대적으로 불안정)이 끊기거나 크래시해도 디스코드 봇과 대시보드는 영향을 받지 않도록 격리한다.

### 검토한 대안

- **단일 모놀리식 프로세스**: 배포는 가장 단순하지만, node-kakao의 불안정성(재연결 루프, 크래시)이 디스코드 봇과 대시보드까지 함께 죽이는 구조적 리스크가 있어 기각.
- **완전 분리된 마이크로서비스(별도 저장소 + REST/큐 통신)**: 팀/배포 규모가 커질 때 유리하지만, 소규모 친목 모임 규모의 시스템에는 인프라·통신 오버헤드가 과함.

### 카카오톡 봇 구현 방식

카카오톡은 오픈채팅용 공식 봇 API를 제공하지 않는다. `node-kakao`(카카오 자체 프로토콜을 리버스 엔지니어링한 비공식 Node.js 라이브러리)를 사용한다. PC 클라이언트 UI 자동화 방식과 달리 서버에서 직접 상시 구동할 수 있어 나머지 컴포넌트와 같은 VPS에 배포 가능하다. 비공식 프로토콜이므로 계정 정지 및 프로토콜 변경으로 인한 breakage 리스크가 있음을 감수한다 — 메시지 전송 없이 읽기 전용으로만 사용해 리스크를 최소화한다.

## 데이터 모델

```
Member
  id              PK (기본키)
  realName        string
  riotId          string?
  discordUserId   string? unique
  kakaoUserId     string? unique   // node-kakao의 내부 고유 유저 ID. 닉네임이 아님 — 닉네임은 변경될 수 있어 매핑 키로 부적합
  elo             int (기본값 1000)
  lastActiveAt    datetime?        // 카톡방에서 마지막으로 @멘션된 시각

GameResult
  id              PK
  playedAt        datetime
  participants    // Member 참조 + 결과(승/패 또는 순위)

MentionLog
  id                    PK
  mentionedKakaoUserId  string
  mentionedAt           datetime
  rawMessage            string?    // 감사/디버깅용
```

`discordUserId`, `kakaoUserId`는 각각 unique 제약을 가지지만 nullable — 한쪽만 채워진 "반쪽 레코드" 상태를 허용한다.

## 컴포넌트별 책임

**discord-bot**
- ELO 조회 명령어(`/elo`, `/랭킹` 등)만 제공. 조회 전용이며, ELO 계산 로직은 갖지 않고 `packages/core`가 계산한 결과를 DB에서 읽기만 한다.

**kakao-bot**
- 오픈채팅방에 상시 접속해 메시지 수신 이벤트만 구독한다 (전송 없음).
- 메시지에서 `@멘션`을 파싱해 대상 카카오 유저 ID로 `MentionLog`를 insert하고 해당 `Member.lastActiveAt`을 갱신한다.
- 처음 보는 카카오 유저가 멘션되면 `kakaoUserId`만 채운 `Member` 레코드를 자동 생성한다 (관리자가 나중에 대시보드에서 디스코드 계정과 매핑).

**dashboard**
- 회원 관리: 미연결(반쪽 레코드) 목록을 보여주고, 관리자가 디스코드 계정과 카카오 계정을 수동으로 매핑.
- 게임 결과 입력 UI: 참가자는 이미 매핑된 `Member` 중에서만 선택 가능하도록 제한.
- 게임 결과 저장 시 `packages/core`의 ELO 계산 함수를 호출해 관련 `Member.elo`를 갱신 (트랜잭션으로 처리).
- 미활동자 리포트: `lastActiveAt`이 14일 이상 지난 `Member`를 조회 시점에 실시간 쿼리로 보여준다 (별도 배치/스케줄러 불필요).
- 반쪽 레코드(미연결 회원)는 정상적으로 ELO/활동 집계에 포함시키되, 목록에 "미연결" 배지를 표시한다.

**packages/core**
- ELO 계산 함수와 미활동 판정 쿼리 로직을 순수 함수로 제공. discord-bot과 kakao-bot은 이 패키지에 의존하지 않고 단순 read/write만 수행한다.

## 데이터 플로우

**신규 회원 유입**
1. 카톡방에 새 닉네임이 처음 멘션되거나 디스코드 서버에 새 멤버가 들어오면, 해당 플랫폼 ID만 채운 반쪽 `Member` 레코드가 생성된다.
2. 대시보드의 "미연결 목록"에 노출된다.
3. 관리자가 반대편 플랫폼 계정과 수동으로 매핑하면 완전한 레코드가 된다.

**활동 추적**
1. kakao-bot이 오픈채팅방 메시지를 수신한다.
2. 메시지 내 `@멘션`을 파싱한다 (한 메시지에 여러 명이 멘션될 수 있음 — 각각 처리).
3. 멘션된 각 카카오 유저에 대해 `MentionLog`를 insert하고 `Member.lastActiveAt = now`로 갱신한다.
4. 대시보드는 조회 시점에 `lastActiveAt < now - 14일`인 `Member`를 쿼리해 미활동자 리포트로 보여준다.

**ELO 계산**
1. 관리자가 대시보드에서 게임 결과(참가자 + 승패/순위)를 입력한다.
2. `packages/core`의 ELO 함수가 실행되어 관련 `Member.elo`가 갱신된다 (트랜잭션).
3. discord-bot은 다음 `/elo` 조회 시 갱신된 값을 그대로 읽는다 (푸시 알림 없음, 필요 시 추후 확장 가능).

## 에러 처리 및 안정성

- **kakao-bot**: 비공식 프로토콜 특성상 세션이 끊기는 일이 있을 수 있다. pm2로 감싸 크래시 시 자동 재시작 + 재로그인하며, 잦은 재연결 시도에는 백오프를 적용한다. 재연결 중 유실된 메시지는 구조적 한계로 받아들인다 — 이 시스템은 "완벽한 출석 기록"이 아니라 "대략적인 활동 신호"로 미활동자를 걸러내는 용도이므로 2주 단위 판정에는 충분하다.
- **discord-bot**: 공식 API 기반으로 상대적으로 안정적. 표준적인 명령어 에러 핸들링만 적용한다.
- **dashboard**: 게임 결과 입력 시 참가자가 실제 매핑된 `Member`인지 서버사이드 검증. ELO 재계산은 트랜잭션으로 묶어 부분 실패를 방지한다.
- **DB 동시성**: kakao-bot과 discord-bot이 동시에 신규 `Member`를 upsert할 수 있으므로, `discordUserId`/`kakaoUserId`의 유니크 제약 위반 레이스 컨디션은 upsert 쿼리로 처리한다 (선점 실패 시 기존 레코드를 재사용).

## 테스트 전략

- **packages/core**: ELO 계산은 입력(현재 레이팅, 경기 결과) → 출력(갱신된 레이팅)이 결정적이므로 순수 함수 유닛 테스트로 충분히 커버한다.
- **kakao-bot**: 실제 node-kakao 연결(계정 필요, 비공식 API)은 CI에 부적합하므로 통합 테스트 대상에서 제외한다. "메시지 파싱 → @멘션 추출 → MentionLog/Member 업데이트" 로직만 순수 함수로 분리해 가짜 메시지 객체로 유닛 테스트한다.
- **discord-bot**: discord.js 클라이언트는 목(mock) 처리하고, 명령어 핸들러 로직만 유닛 테스트한다.
- **dashboard**: 매핑 로직(유니크 제약 충돌 처리), ELO 재계산 트리거 API 라우트는 테스트 DB 대상 통합 테스트로 커버한다. UI는 소규모 내부 도구이므로 수동 테스트로 충분하다 (E2E 자동화는 이 규모에 과함).
- 외부 실계정/실API에 의존하는 부분(카카오톡 연결, 디스코드 연결)은 항상 얇은 어댑터로 분리하고, 그 안쪽 로직만 테스트 대상으로 삼는다.
